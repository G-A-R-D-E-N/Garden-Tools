# VMAD array element decoding

`Radicle/src/schema/vmad.cpp:read_property` now decodes the elements of the five scalar array types instead of skipping them: object array (11), string array (12), int array (13), float array (14) and bool array (15). Each array's `u32` count is consumed and every element is read into the matching optional vector on `Radicle/include/fo4/schema/vmad.hpp:VmadProperty` (`object_elements`, `text_elements`, `integer_elements`, `real_elements`, `boolean_elements`). Exactly one of these is engaged, and only for its own array type; an empty array engages its vector as empty.

The byte layout mirrors the existing `Radicle/src/schema/vmad.cpp:walk_property` walker, so the typed reader and the offset scanner consume identical bytes. Object elements go through the new `Radicle/src/schema/vmad.cpp:read_object_element` helper, which is also used by the scalar object case, so an unexposed nonzero unused word throws `UnsupportedVmadProperty` for array elements exactly as it does for scalars. Float elements go through `Radicle/src/schema/vmad.cpp:read_float`, which is shared with the scalar float case, so values are reconstructed from the raw bit pattern and `-0.0` keeps its sign bit.

Struct (7) and struct array (17) properties remain count-only: `element_count` is set and member properties are walked with `walk_properties` but not exposed. Variable (6) and variable array (16) still throw `UnsupportedVmadProperty`. `VmadProperty::element_count` is still set for every array and struct type, as before. The `*_elements` fields for struct and struct array stay disengaged.

In this section, no C ABI, `RADICLE_ABI_VERSION`, environment, placed-record, or binding code changed. The header additions are the `VmadObjectElement` struct and the five optional vector fields only.

Tests: `Radicle/tests/test_vmad.cpp` adds ten `VmadArrayElements.*` cases. Before the reader change, nine failed (optional array fields were disengaged) and the struct case passed, since struct behavior is unchanged. After the change, all ten pass. The full `fo4_tests` run reports 824 passed, 38 skipped (pre-existing optional-data skips) and 0 failed out of 862.

## Placed reference script elements

`Radicle/src/environment/placed.cpp:decode_scripts` resolves each object array element's `object` through `env_.resolve_link` into the new `Radicle/include/fo4/environment/placed.hpp:ScriptProperty::object_elements` (`std::optional<std::vector<FormKey>>`), the same resolution the scalar `object` uses. The string, int, float and bool elements are not copied into `ScriptProperty`; the C layer reads them from the raw `VmadProperty` vectors, as it already does for scalar text, integer, real and boolean.

`Radicle/src/c_api_placed.cpp:build_view` emits one `radicle_script_element` vector per script property (`PlacedHolder::elements`, one entry for every property). The outer vector is reserved to the total property count before the script loop, so an inner `data()` pointer stored in `radicle_script_property::elements` is never invalidated by a later `emplace_back`. Element text points into the raw property strings owned by `PlacedHolder::data`, the same storage the scalar `text` uses. String array elements go through the same windows-1252 to UTF-8 conversion as scalar text, in the first loop of `build_view`, so they match scalars.

`Radicle/include/fo4/c_api_env.h:radicle_script_element` has `object`, `alias`, `text`, `integer`, `real` and `boolean`; each array kind sets only its own member and the rest stay zero or null. `radicle_script_property` appends `has_elements`, `elements` and `element_value_count`. `has_elements` is 1 exactly when one of the five vectors is engaged, which is types 11 through 15. An empty array gives `has_elements` 1, `element_value_count` 0 and a possibly null `elements`. A struct (7) keeps `has_elements` 0 and `has_element_count` 1.

## Unknown property types stop the typed reader

- `Radicle/src/schema/vmad.cpp:read_property`: an unknown property type (anything other than 0-5, 7, 11-15 and 17) throws `UnsupportedVmadProperty` instead of `parse_error`.
  - `read_vmad_scripts` therefore returns the properties already read with `unsupported = true`, the same as for types 6 and 16, instead of failing the whole record.
  - This matches an unmerged decompile of Fallout4.exe OG 1.10.163 (ReverseEng/Fallout4_Runtime_Research pull request #11, `vmad-variable-types-388`; GardenEngine issue #355). In it the per-property reader rejects types 8, 9, 10 and >= 18 before reading a value, and the failure ends that script's property loop while keeping the earlier properties. AE was not checked.
- `Radicle/src/schema/vmad.cpp:walk_property` (form-link scan and master remap) also throws `UnsupportedVmadProperty` for an unknown type, at top level or nested inside a struct. `vmad_coverage` then reports `unsupported` and `failed`, so master remap still refuses. #409 made `Radicle/tests/test_vmad_unsupported.cpp:expect_remap_refused` assert `vmad_has_unsupported_properties`, which a `parse_error` left false for `UnsupportedPropertyTypesRefuseMasterRemap` (type 8). A struct-nested unknown type likewise makes `read_vmad_scripts` return `unsupported` instead of throwing.
- `Radicle/tests/vmad_writer_fixture.hpp:payload` and `Radicle/bindings/csharp/Radicle.Interop.Tests/VmadAuthoringTests.cs:Vmad` write a zero unused object word. #452 made `walk_object` and `read_object_element` refuse a nonzero one, and the earlier 0xBEEF fixture word made every VMAD writer test fail coverage after #409 landed.
- `Radicle/src/schema/vmad.cpp:read_quest_vmad_extras` still reports `unsupported`, but its reason is now the generic quest-extras text, not the parse message.
- Regression: `Radicle/tests/test_vmad_unsupported.cpp:UnknownPropertyTypesStopTheTypedReaderLikeVariables` covers types 8, 9, 10, 18 and 255.
  - It failed before the change with `plugin parse error at 0x31: unknown VMAD property type`.
  - After the change `fo4_tests` passed 827, skipped 38 (real-data and corpus tests) and failed 0 of 865.

## Quest property array elements

`Radicle/src/c_api_quest.cpp:radicle_quest_runtime_properties` makes one `ElementStore` per call. It holds the quest context from `fo4::plugin_form_id_context`, the plugin names of object elements in a `std::deque` so their pointers stay valid, and one element vector per property. `Radicle/src/c_api_quest.cpp:append_elements` copies only the vector the typed reader engaged, so `has_elements` is 1 only when every element was decoded. A struct (7) or struct array (17) has no element vector, so it keeps `has_elements` 0 and its `element_count`.

Object elements resolve through `fo4::resolve_plugin_link` with the quest plugin's context, because `radicle_script_element::object` is a `radicle_form_key` (plugin and local ID) and the quest path has no environment. The scalar quest `object_form_id` stays a raw form ID; only the element form is resolved. A NULL form ID gives a NULL plugin and local ID 0.

`Radicle/src/c_api_quest.cpp:copy_elements` deep-copies each element's text and plugin name, since the store and the reader's `VmadProperty` strings are gone when the call returns. `Radicle/src/c_api_quest.cpp:free_owned` releases them, and `Radicle/src/c_api_quest.cpp:radicle_free_quest_properties` calls it for every property.

The alias-script owner shares this decode: script, fragment and alias-script properties all go through `Radicle/src/c_api_quest.cpp:append_properties`, which calls `append_elements`.

Element text is NUL-terminated, because `radicle_script_element` has no size field, so an embedded NUL ends an element string. The placed path has the same limit.

ABI: `Radicle/include/fo4/c_api.h:RADICLE_ABI_VERSION` is 29 with the three members appended to `Radicle/include/fo4/c_api_quest.h:radicle_quest_property`. `Radicle/include/fo4/c_api_quest.h` includes `fo4/c_api_env.h` to reuse `radicle_script_element`, which stays defined there. The managed value is `Radicle/bindings/csharp/Radicle.Interop/QuestRuntime.cs:QuestRuntimeValue` with `Elements`, next to `ElementCount`.

## Struct members

This section supersedes the struct line of the first section for structs whose members are all scalars or objects. The rest of that section still holds. The ten `VmadArrayElements.*` cases are in `Radicle/tests/test_vmad_array_elements.cpp`, not `Radicle/tests/test_vmad.cpp` as that section says.

Papyrus structs cannot hold structs, arrays, `Var` or `const` members (`Structs_(Papyrus).html` in the offline Creation Kit wiki, Nexus file 52183, `FO4CKWiki_210520/fallout4/`). A struct member is therefore type 1 to 5 (object, string, int, float, bool), and every other member type leaves the struct undecoded.

- `Radicle/src/schema/vmad.cpp:read_property` takes a copy of the slice before the walk for types 7 and 17. The walk is still `walk_properties`, so the consumed bytes do not change. `Radicle/src/schema/vmad.cpp:decode_structs` decodes the copy into `VmadProperty::struct_elements`: one struct for type 7, `n` for type 17, and an empty array is engaged as empty.
- `Radicle/src/schema/vmad.cpp:read_struct_members` reads one struct: a u32 member count, then each member's name, type, flags and scalar value. A member of any other type makes it return false, which leaves `struct_elements` disengaged. It does not throw.
- An object member whose unused word is not zero is refused by `walk_object`, which `read_property` runs over struct members before `decode_structs`. So `read_vmad_scripts` marks the record unsupported, keeps only the properties before it, and `scan_vmad` refuses the record, the same as a scalar object word (see `radicle-vmad-opaque-word-20261008.md`). The struct is not left disengaged. `decode_structs` still catches `UnsupportedVmadProperty` from `read_object_element`, but the walk has already refused that case. Test: `Radicle/tests/test_vmad_array_elements.cpp:StructWithUnexposedObjectWordStopsTheTypedReader`.
- A variable (6) or variable array (16) member still throws from `walk_property`, as it did before.
- Placed: `Radicle/include/fo4/environment/placed.hpp:ScriptProperty::struct_member_objects` holds one resolved key per struct member (nullopt for a non-object member). `Radicle/src/environment/placed.cpp:decode_scripts` fills it with `env_.resolve_link`. `Radicle/src/c_api_placed.cpp:build_view` converts member names from windows-1252 and passes member text through as UTF-8, then fills `PlacedHolder::structs` and `PlacedHolder::struct_members`. Both are vectors of vectors, so the buffers that `radicle_script_property::structs` points at survive later emplacements.
- Quest: `Radicle/src/c_api_quest.cpp:append_structs` fills `ElementStore::members` and `ElementStore::structs`, both vectors of vectors, and resolves object members through `element_form_key`, which keeps their plugin strings in the `ElementStore::plugins` deque. `Radicle/src/c_api_quest.cpp:copy_structs` and `copy_members` deep copy each member name, object plugin and text. `free_structs` and `free_members` release them from `free_owned`, which `radicle_free_quest_properties` calls.
- ABI: `Radicle/include/fo4/c_api.h:RADICLE_ABI_VERSION` is 29. `Radicle/include/fo4/c_api_env.h:radicle_script_struct_member` and `radicle_script_struct` are new. `radicle_script_property` and `radicle_quest_property` each append `has_structs` (`uint8_t`), `structs` and `struct_count`, after their element fields. `has_structs` is 1 only when the struct value was decoded.
- Managed: `Radicle/bindings/csharp/Radicle.Interop/PlacedReferences.cs:ScriptStructMember`, `ScriptStruct`, `ScriptProperty.Structs` and `RadicleEnvironment.ScriptStructs`, and `Radicle/bindings/csharp/Radicle.Interop/QuestRuntime.cs:QuestRuntimeValue.Structs`. `Radicle/bindings/csharp/Radicle.Interop/RadicleNative.g.cs` and `Radicle/bindings/csharp/tests/abi_layout_probe.cpp` are regenerated by `Radicle/bindings/csharp/tools/generate_interop.py`.
- Tests, written in the change that added this section and not run there: `Radicle/tests/test_vmad_array_elements.cpp:StructDecodesScalarAndObjectMembersInFileOrder`, `StructArrayDecodesEachStructInOrder`, `EmptyStructArrayIsEngagedAndEmpty`, `StructWithNonScalarMemberStaysDisengagedAndInSync` and `StructWithUnexposedObjectWordStopsTheTypedReader`; `Radicle/tests/test_c_api_quest.cpp:ReportsDecodedStructMembersForEveryOwner`; `Radicle/tests/test_environment_script_elements.cpp:CApiExposesDecodedStructMembersAndStructArrays`; and the managed `ExposesDecodedStructMembersAndStructArrays` and `ExposesDecodedStructMembersForScriptFragmentAndAliasOwners` in `Radicle/bindings/csharp/Radicle.Interop.Tests/PlacedScriptElementTests.cs` and `QuestScriptElementTests.cs`.
- A struct whose member is an array stays disengaged while the walk keeps the following properties in sync: `Radicle/tests/test_c_api_quest.cpp:CApiQuest.DisengagedStructWithArrayMemberStaysInSync`. Names are converted from Windows-1252 and text values (scalar text, string-array elements and struct member text) pass through as UTF-8, matching xEdit `wbInterface.pas:23867` (names, wbLenString, Windows-1252) and `wbInterface.pas:23869` (`wbEncodingVMAD := TEncoding.UTF8`), and `wbDefinitionsFO4.pas:3771`/`:3778` for struct member and array String types. Test: `Radicle/tests/test_environment_script_elements.cpp:PlacedScriptElementTest.CApiConvertsWindows1252NamesKeepsUtf8Text`.

## Quest property text and struct-then-scalar reads

- `Radicle/bindings/csharp/Radicle.Interop/QuestRuntime.cs:QuestRuntimeValue` keeps quest property text byte-preserving on purpose: `Text` is `Encoding.Latin1.GetString` of the raw stored VMAD bytes and `TextBytes` is `Encoding.Latin1.GetBytes(Text)`, so every byte, invalid UTF-8 included, round-trips. xEdit reads VMAD text as UTF-8 (`wbInterface.pas:23869`), and Radicle's writer stores UTF-8 (`Radicle/src/c_api_vmad.cpp`, GT-164), so a consumer wanting xEdit's string decodes `TextBytes` with `Encoding.UTF8`. `Radicle/bindings/csharp/Radicle.Interop/PlacedReferences.cs:ScriptProperty` decodes placed-script text as UTF-8 instead, which replaces invalid bytes with U+FFFD. Test: `Radicle/bindings/csharp/Radicle.Interop.Tests/QuestRuntimeAttachmentTests.cs:Utf8AndInvalidBytesSurviveTheRowMapping`.
- `Radicle/tests/test_vmad_array_elements.cpp:StructFollowedByScalarReadsBoth` covers a non-empty struct (type 7) with one int member, followed by an int property. `Radicle/src/schema/vmad.cpp:read_property` copies the slice before `walk_properties` and decodes the copy with `decode_structs`, so the cursor ends at the next property. `Radicle/src/schema/vmad.cpp:read_struct_members` reads a u32 member count, then for each member its name, type, flags and value.
