# VMAD scalar object support boundary

`Radicle/src/schema/vmad.cpp:read_property` reads scalar object properties in both existing object formats. The typed model does not expose the additional unsigned 16-bit word. Accepting a nonzero word while discarding it therefore makes a lossy projection appear fully supported. The reader now treats that case as `UnsupportedVmadProperty`, using the existing partial-result path. Zero remains the existing local support policy; this does not establish engine validity or that the word has no runtime meaning.

The independently maintained parser at `opencw/third_party/Mutagen/Mutagen.Bethesda.Fallout4/Records/Common Subrecords/AVirtualMachineAdapter.cs:FillObject` in GardenEngine reads the same word into `Unused`, and `WriteObject` writes it back in both formats. Its inspected SHA-256 is `1b0f481207c414b2c1ea87206e9a19ba2aef9c664660bc7c45f10619352e8b32`. This is public parser/model evidence; Fallout runtime meaning remains unverified. CommonLib is unchanged.

`Radicle/src/schema/vmad.cpp:read_vmad_scripts` retains preceding properties and marks the script list unsupported before publishing the affected property. `read_quest_vmad_extras` uses the same scalar reader for fragment and alias-script properties. `Radicle/src/quest/runtime.cpp:quest_runtime_data` and the quest-extra reader describe an unsupported property rather than claiming its type alone caused the refusal.

`Radicle/src/c_api_placed.cpp:build_view` already publishes the reader's unsupported flag as `scripts_unsupported`. GardenEngine's `opencw/Services/CellCompiler.RefNodes.cs:AppendRefMetadata` carries that flag to the compiled reference, and `opencw/OpenCw.Papyrus/Vm/GameSession.cs:AttachReference` refuses unsupported sources before binding or initialization. The change adds no ABI field/version and promotes no evidence gate.

`Radicle/src/schema/vmad.cpp:require_zero_unused_word` is the single check for the unused word of an object value (xEdit reads it as `wbUnused(2)` in both object formats, `source:xEdit Core/wbDefinitionsFO4.pas:3728-3752 @93cc0bc5`, and does not check its value; the zero-only rule is local policy). `Radicle/src/schema/vmad.cpp:read_property` and `Radicle/src/schema/vmad.cpp:walk_object` both call it, so the typed reader and the scan path agree. Because `read_property` decodes object arrays and struct members through `walk_object`, a nonzero word inside those is also refused by the reader and reported as unsupported. The scan path refuses it through `Radicle/src/schema/vmad.cpp:scan_vmad`, which makes `vmad_coverage` incomplete and `vmad_formid_offsets_for_remap` return no offsets, so remapping refuses that record instead of rewriting form IDs in it. In the papyrus census (`Radicle/tools/parity/main.cpp:dump_papyrus`) such a record is reported as `incomplete-vmad`, the same as other refusals. Quest alias headers still ignore their unused word in both paths, and this is not a general rejection of every opaque word.

`Radicle/tests/test_vmad_unsupported.cpp:UnexposedScalarObjectWordsStopTheScanPath` covers formats 1 and 2 with words 0, 1 and 65535 on the scan path: nonzero words make coverage unsupported and incomplete and withhold remap offsets, zero words stay complete.

`Radicle/tests/test_vmad_unsupported.cpp:UnexposedScalarObjectWordsStopTheTypedReader` covers formats 1 and 2 with words 0, 1 and 65535, retained preceding properties, unchanged zero-word form ID/alias values, and exact plugin read/write byte preservation. `Radicle/tests/test_environment_placed.cpp:CApiReportsUnexposedScalarObjectWords` checks the public placed-reference flag and property projection with the same inputs.

`Radicle/src/schema/vmad.cpp:walk_script_entry` and `Radicle/src/schema/vmad.cpp:read_vmad_scripts` read the flags byte and property count for every script entry, including one with an empty name. The same rule covers alias scripts in `Radicle/src/schema/vmad.cpp:read_quest_vmad_extras` and `Radicle/src/schema/vmad.cpp:walk_quest_extra`, and the PERK, TERM, PACK, INFO and SCEN fragment headers handled by `walk_indexed_fragments` and `walk_flagged_fragments`. xEdit defines the entry as ScriptName, flags and properties with no empty-name exception (`source:xEdit Core/wbDefinitionsFO4.pas:3861-3865 @93cc0bc5`, `wbScriptEntry`), and uses it for the leading list (`:3884`), the fragment headers (`:3905`, `:3935`, `:3958`, `:4036`) and alias scripts (`:4015`). Only the QUST fragment header skips them when the name is empty (`source:xEdit Core/wbDefinitionsFO4.pas:3983-3990 @93cc0bc5`, `source:xEdit Core/wbDefinitionsCommon.pas:5866 @93cc0bc5`, `wbScriptFragmentsEmptyScriptDecider`), which is why `walk_quest_extra` and `read_quest_vmad_extras` keep that one skip. A 2026-10-11 scan of the official masters found 0 empty-named entries in leading script lists (20,172 VMADs), so no vanilla data exercises this path; the rule is xEdit's, not corpus-proven. `walk_script_entry` still returns false for an empty name, so `fragment_script_count` counts only named fragment headers, as in the QUST case. Tests: `Radicle/tests/test_vmad_unsupported.cpp:EmptyLeadingScriptNameKeepsFlagsPropertiesAndOffsets` and `Radicle/tests/test_vmad_unsupported.cpp:EmptyQuestFragmentHeaderHasNoFlagsOrProperties`.
