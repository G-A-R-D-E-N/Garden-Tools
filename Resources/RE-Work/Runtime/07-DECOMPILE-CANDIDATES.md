# 07 -- Decompile Verification of the 313 Candidate CommonLib Misname Bugs (2026-07-10)

Full decompile-based verification pass over every one of the 313 candidates flagged by [06-FUNCTION-INDEX.md](./06-FUNCTION-INDEX.md)'s 1.10.155-vs-1.10.163 cross-reference. Each candidate's function was batch-decompiled (Scripts/DecompileCandidates.java, raw output in Decompiles/<address>.txt), then independently judged by parallel review agents against the actual decompiled C body -- not just the competing name text. See the methodology note at the bottom for exactly how this was run and its limitations.

## Results

**313 candidates reviewed, 0 skipped, 0 decompile failures.**

| Verdict | Count | % | Meaning |
|---|---:|---:|---|
| `CONFIRMED_MISNAME` | 150 | 48% | The decompiled body's actual behavior matches the community-decoded name and contradicts the CommonLib name -- a real bug, same class as the two originally-confirmed ones. |
| `FOLDED_ALIAS` | 68 | 22% | Body is a trivial thunk/forwarder/empty stub. Very likely MSVC identical-COMDAT-folding (the linker merges byte-identical trivial functions from unrelated classes onto one shared address) -- not a naming bug, a compiler artifact. New pattern discovered during this pass, not previously documented. |
| `EXISTING_ACTUALLY_RIGHT` | 63 | 20% | The CURRENT CommonLib name was actually correct; the 1.10.155 cross-reference match was misleading (case-only difference, synonym, or a legitimate second name for the same thing). Real finding: the cross-reference methodology itself has a nontrivial false-positive rate. |
| `INCONCLUSIVE` | 32 | 10% | Decompiled body doesn't clearly support either name (generic virtual-dispatch stub, unimplemented-trap boilerplate, or a bare unscoped placeholder that isn't actually contradicted by anything). |

## Applied to the Ghidra project (2026-07-10, same day)

**137 of the 150 CONFIRMED_MISNAME renames were applied** to `Projects\fwgh_proj_1.10.163_unpacked`
(`Scripts\ApplyConfirmedMisnames.java`) -- addresses re-demangled from the original community-label
mangled string where possible (full namespace+signature, matching PDB-import fidelity) with a
forced `setName(..., USER_DEFINED)` fallback. **13 were reverted** after a post-apply cross-check
against CommonLibF4's own hand-authored headers (`CommonLibF4\include\`, the canonical copy) found
that the OLD name was, in every one of the 13 cases, a real, exactly-matching member already
declared on that exact class -- often with an explicit vtable-slot comment (`// 01`, `// 4C`, etc.)
corroborating it. CommonLibF4's headers are more authoritative than a decompile-only LLM read (they
represent hand-verified engine ports, sometimes cross-checked against other titles' debug symbols);
the review agents simply didn't have access to them. The 13 reverted addresses: `ImageSpaceEffectGetHit::Render`,
`Movie::GetCurrentFrame`, `Scaleform::GFx::Value::ObjectRelease`, `bhkCharacterController::ClearCollectorDataImpl`,
`bhkCharacterController::ApplyMoveImmediately`, `MemoryHeap::GetStats`, `MemoryHeap::FreeSysDirect`,
`MemoryHeap::AllocSysDirect`, `MemoryHeap::GetAllocHeap`, `PipboyManager::OnMouseMoveEvent`,
`ExamineMenu::OnThumbstickEvent`, `TESLeveledList::GetCanContainFormsOfType`, `MagicItem::CopyMagicItemData`
(`Organized\misnames_to_revert_simple.csv`, `Scripts\RevertMisapplied.java`).

**Also checked:** grepped all 137 applied old (wrong) names against every plugin's C++ source under
`Projects\` and the canonical `CommonLibF4\include\` -- zero hits. No live hook or plugin code
depended on any of the wrong names, so applying the corrections carried no behavioral risk to
existing plugins.

**Methodology lesson for next time:** cross-check candidates against CommonLibF4's own headers
*before* applying, not after -- it would have caught these 13 before they were ever written to the
Ghidra project, instead of requiring a revert pass. Two independent sources (1.10.155 PDB +
decompile) agreeing was NOT sufficient in these 13 cases; a third source (CommonLibF4's own
hand-verified headers, when one exists for the class) should be checked first when available.

Final tally: **137 real naming bugs corrected** in the Ghidra project, **13 false positives caught
and reverted**, **0 regressions to live plugin code**. `Organized\applied_misname_corrections.csv`
has the full per-address apply log.

## FOLDED_ALIAS -- likely linker code-folding, not bugs (68)

**New pattern discovered during this pass.** MSVC/link.exe's identical-COMDAT-folding (ICF) merges functions with byte-identical generated machine code -- across completely unrelated classes -- onto a single shared address. A trivial one-line wrapper (return GetTickCount64();) and an IAT thunk for the same API can be genuinely, legitimately the same address under two different "correct" names. These are NOT naming bugs; don't "fix" them by picking one name over the other -- both may be valid depending on which call site you're reasoning about. Recognizable pattern: body is empty (return;), a single trivial forwarding call, or a 1-3 line thunk with no class-specific field/data access.

## Methodology

1. Scripts/DecompileCandidates.java batch-decompiled all 313 addresses from Organized/crossref_review_candidates.csv in one headless Ghidra run (~2 min total -- batching into one run instead of 313 separate analyzeHeadless invocations avoided ~2-5 hours of pure JVM/project-load overhead). Each candidate's raw decompile is at Decompiles/<address>.txt, including Ghidra's own current name/signature for whatever function actually contains that address (a live re-check, not just trusting the CSV).
2. The 313 candidates were split into 8 batches and reviewed in parallel by independent general-purpose agents, each instructed to read the actual decompiled C body (function calls made, fields accessed, control flow, string/constant references) as evidence -- explicitly told not to pattern-match on the name text alone, and given the FOLDED_ALIAS category with a worked example so trivial thunks wouldn't get miscounted as bugs.
3. Verdicts were parsed back out, deduplicated by address, and joined against the original existing/decoded name claims.

**Limitations:** this is single-pass LLM judgment per candidate, not independently cross-checked by a second reviewer or a human. The reasoning given is generally concrete (cites actual calls/fields/strings from the decompile), which is a meaningfully stronger evidentiary bar than the original disagreement-list heuristic alone, but individual verdicts -- especially on the boundary between CONFIRMED_MISNAME and EXISTING_ACTUALLY_RIGHT for functions with genuinely dual-purpose-sounding names -- should still be treated as strong leads, not ground truth, before being used to justify a live hook address change.
