# Quests subsystem — architecture notes

Companion doc to [`Quests.txt`](Quests.txt) (the raw bucketed function list, 6,064 functions in
1.10.163, ~0.8% still placeholder-named — this subsystem is unusually well-named already thanks to
CommonLibF4 RTTI matching + the community label pass). This file is the narrative layer: what the
classes actually do, based on live decompiles against `fwgh_proj_1.10.163_unpacked`, not just names.

Regenerated by `python ReverseEngineering/Scripts/organize_functions.py` (category `Quests`, added
2026-07-11 — previously these functions were unlabeled and scattered across `Forms_TES` /
`Forms_BGS` / `Misc_Uncategorized`, indistinguishable from every other TES/BGS form type).

## Class families in this bucket

| Family | Role |
|---|---|
| `TESQuest`, `TESQuestStage`, `TESQuestTarget`, `QUEST_DATA`, `QUEST_STAGE_DATA` | The quest record itself: stage list, flags, current/highest stage reached |
| `BGSBaseAlias`, `BGSRefAlias`, `BGSLocAlias`, `BGSRefAliasInstanceData`, `ExtraAliasInstanceArray` | Quest aliases — the indirection layer between a quest and the actors/objects/locations it operates on |
| `BGSQuestObjective`, `BGSInstancedQuestObjective`, `BGSQuestInstanceText`, `QUEST_OBJECTIVE_STATE` | Objective text/state shown in the Pip-Boy quest log |
| `BGSScene`, `BGSSceneAction*` (Dialogue/NPCResponseDialogue/PlayerDialogue/Radio/StartScene/Timer/Package), `BGSScenePhase` | Scripted scene/dialogue playback (cutscene-style scenes, not the 3D scene graph — see naming note below) |
| `TESTopic`, `TESTopicInfo`, `BGSTopicSubtypeUnion`, `MenuTopicManager`, `SayOnceTopicInfos` | Dialogue topic tree (what the player/NPC can say) |
| `BGSStoryManager*` (BranchNode/EventNode/NodeBase/QuestNode/TreeForm/TreeVisitor) | The Story Manager — Bethesda's procedural "which quest/event should fire now" evaluator, walks a tree of condition nodes |
| `GameScript::QuestMgrInternal::*`, `GameScript::QuestCallbackMgr` | The Papyrus↔quest bridge: native `Quest.*` script functions, latent `WaitForQuestStage`/`WaitForQuestStart` |

**Naming note:** the category predicate matches `BGSScene`/`SceneAction`/`ScenePhase`/`SCENE_`
specifically, *not* bare `"Scene"` — that substring would also catch `SceneGraph`/`BSSceneGraph`
(the unrelated 3D renderer scene graph), which correctly stay out of this bucket.

## Confirmed: `TESQuest::SetStage` (RVA `0x5d71e0`, unqualified `SetStage` in the DB)

Decompiled directly (`fwgh_proj_1.10.163_unpacked`). CommonLibF4's own header (`RE/T/TESQuest.h`)
already declares this via `ID::TESQuest::SetStage`, confirming the address; the Ghidra DB just never
got the `TESQuest::` qualifier applied to the symbol name.

```
bool TESQuest::SetStage(TESQuest* this, uint16_t stageID)
```

- **Gate:** refuses immediately unless `(this->flags /* QUEST_DATA @ 0xf4 */ & 1) != 0` — bit 0 of
  the quest's flags byte. This is the exact mechanism already documented in memory
  `reference_quest_setstage_dormant_esl.md` ("SetStage silently no-ops unless QUEST_DATA.flags bit0
  is set") — this decompile is now the *proof*, not just an inference.
- **Lookup:** walks an open-addressing hash table at `this+0x138`/`this+0x144` (mask-based probe,
  chained via the low 16 bits of each bucket entry) keyed by stage ID, to find the matching
  `TESQuestStage*` in the stage array at `this+0x100`.
- **On match:** calls `TESQuestStage::SetDone(stage, quest, false)` (the real per-stage completion
  logic — not inlined here, a separate function worth decompiling next if stage-completion behavior
  is ever in question), bumps `this+0x2b4` (highest-stage-reached, ushort) if the new stage is
  higher, marks the quest dirty via a vtable call (slot 0xD, arg `0x80000000` — the same "top-bit
  dirty flag" convention seen elsewhere in the engine, e.g. `HUDMenu`'s ctor), and broadcasts a
  global `BSTEventSource<TESQuestEvent::Event>::Notify` (matches `RE::TESQuestEvent` in CommonLibF4).
- **On no match:** silently returns false (stage ID not found in this quest's stage list) — a second,
  distinct "no-op" case from the flags-bit gate above.

**Full circle: `TESQuestStageItem::Resolve`** (RVA `0x5f96b0`, the per-log-entry action `SetDone`
calls for each entry) — this is the exact mechanism behind three CK per-log-entry checkboxes,
confirmed with their precise flag bits:

- Skips its own condition check when called with `alsoRun=true` (matches the `bVar2`/`param_2` flow
  in `SetDone`); otherwise evaluates its own embedded `TESCondition` (the class itself extends/embeds
  one — `Resolve` casts `this` directly to `TESCondition*`) and bails if false.
- **Flag bit 0** set → `TESQuest::SetCompleted(quest, true)` + `PlayerCharacter::RemoveQuestTargets`
  — the CK "Complete Quest" per-log-entry checkbox.
- **Flag bit 1** set → `TESQuest::SetFailed(quest, true)` + `RemoveQuestTargets` — the CK "Fail Quest"
  checkbox.
- A separate byte field (`+0x16`, nonzero) → calls `PlayerCharacter::AddQuestStageItem` (adds this
  entry to the tracked quest log) and `TESQuest::SetCurrentJournalText` — the CK "Display in Journal"
  behavior, driving what actually shows up in the Pip-Boy quest log.
- Finally allocates a `StageItemFinishedCallback` object (own vtable, `VTABLE___StageItemFinishedCallback`)
  — the async completion notification, almost certainly what eventually reaches Papyrus's per-stage
  `OnStageSet`-adjacent script fragment dispatch (not itself traced further).

## Confirmed: the Papyrus `Quest.SetCurrentStageID` native bridge

Found via `FindCallers.java` on `SetStage`'s RVA. The Papyrus-side native implementation
(`GameScript::...Quest_SetCurrentStageID...`, RVA `0x1449550`) has its own, EARLIER gate before it
ever reaches `SetStage`:

```
if (!(quest->flags & 1) && quest->eventScopedOwnerID != -1 /* @ +0xf8 */)
    error("attempting to start event scoped quest outside of story manager");
```

This is the literal, exact error string the engine logs — a stronger, more actionable version of the
existing memory note. It also confirms `TESQuest::EnsureQuestStarted(quest, &out_alreadyRunning,
bool)` is the real "auto-start the quest if it isn't running yet" gate used by *both* the Papyrus
bridge and `BGSQuestPerkEntry::ApplyPerkEntry` (perk-driven quest stage advancement) — i.e. any C++
code that wants to safely advance a quest stage should call `EnsureQuestStarted` first, exactly like
these two call sites do, rather than assuming the quest is already running.

## Confirmed: `TESQuestStage::SetDone` — the real per-stage completion logic

Two overloads exist, decompiled in full (recorded in `DECOMPILE-RECORDS.md`, category `Quests`).
**Correction to the earlier note above:** they are NOT a wrapper/helper pair — they're independent,
parallel setters of the same bit.

- **`SetDone(TESQuestStage*, bool)`** (RVA `0x5f7c00`) — trivial: sets or clears bit 0 of the
  stage's own flags byte (`stage+0x1a`) directly. No side effects. Used wherever code just needs to
  flip the "done" bit without triggering log/story-manager notification (e.g. save-game load,
  or a "reset stage" path).
- **`SetDone(TESQuestStage*, TESQuest*, bool)`** (RVA `0x5f90b0` — this is the one `TESQuest::SetStage`
  actually calls) — the real completion logic:
  - **Idempotency guard:** if the stage is already marked done (`stage+0x1a` bit 0 set) AND the quest
    is null or doesn't have flag bit 3 set, returns `false` immediately — a second, distinct no-op
    case beyond `SetStage`'s own quest-enabled gate.
  - Sets the done bit, then reads bits 1/2 of the stage flags (`bVar2`, likely the CK stage
    checkboxes controlling quest-log/radiant visibility) and bit 3 (if set, calls
    `TESQuest::SetKeepInstance(quest, true)` — CK's "Keep Instance" per-stage checkbox).
  - Iterates the stage's log-entry array (`TESQuestStageItem[]`); for each entry, if `bVar2`, calls
    `BGSStoryTeller::AddWaitingStageForQuest(questFormID, stageID, logEntryIndex)` — registers the
    stage with the global Story Teller for later radiant/aggregate pickup — then calls
    `TESQuestStageItem::Resolve(entry, alsoRun)` to actually apply the log entry (quest-log text,
    objective updates). Returns whether there were any log entries processed.

## Confirmed: the Visitor pattern's dispatch mechanism (Story Manager tree walk)

Decompiled all three `AcceptVisitor` overrides found this pass. Each is a thin, one-line virtual
dispatch to the matching `Visit*` method on the passed-in `BGSStoryManagerTreeVisitor`, confirming
the pattern works exactly as `BGSStoryManagerTreeVisitor.h`'s vtable-slot comments declare:

| Node type | RVA | Dispatches to (via visitor vtable slot) |
|---|---|---|
| `TESQuest::AcceptVisitor` | `0x5d7e40` | slot 3 = `VisitQuest(quest)` |
| `BGSStoryManagerBranchNode::AcceptVisitor` | `0x7f13e0` | slot 1 = `VisitBranchNode(node)` |
| `BGSStoryManagerQuestNode::AcceptVisitor` | `0x7f5f80` | slot 2 = `VisitQuestNode(node, canReset=true)` — hardcodes `canReset=true` from this call path |

## Confirmed: `BGSStoryManagerQuestFinder` — the concrete visitor, i.e. the real radiant quest picker

Searching for the `Visit*` method NAMES directly (rather than `BGSStoryManager::`) surfaced their
real owning class: **`BGSStoryManagerQuestFinder`**. This is the actual implementation of
`BGSStoryManagerTreeVisitor` that walks the story manager tree to pick which quest/radiant event
fires. All three methods decompiled in full (they're large; full C in `DECOMPILE-RECORDS.md`).
High-confidence facts extracted:

- **`VisitBranchNode`** — evaluates the branch's `TESCondition` via `ConditionCheckParams`, then
  either walks children **in order** or, if a per-node "random" flag is set
  (`node_flags & 0x1`... exact bit not pinned down, checked via `(byte)node+0x3c & 1`), does
  **weighted-random child selection** via `BSRandom::Int(0, remainingCount)` with rejection sampling
  over already-excluded children. So branch nodes support both sequential AND randomized traversal —
  this is a real, CK-authorable behavior, not just theoretical.
- **`VisitQuestNode`** — the core cooldown/eligibility filter, run per-candidate-quest under a branch:
  - Uses a **scatter-table visited-node cache** (`BSTScatterTableKernel<BGSStoryManagerQuestNode*,
    uint>`) to memoize/avoid re-visiting the same node twice in one evaluation pass.
  - Skips quests already running (`BGSStoryTeller::GetIsQuestStarted`).
  - **Cooldown timer**: compares `BGSStoryManagerQuestNode::GetQuestHoursUntilReset(node, quest)`
    against `Calendar::GetDaysPassedExact()` and a per-candidate last-fired timestamp stored in a
    float array on the node (`node+200`, indexed per quest candidate) — this IS the radiant-quest
    "don't repeat too soon" mechanism, confirmed in code, not inferred from behavior.
  - **Weighted-random candidate selection with rejection sampling**: among still-eligible candidates,
    picks a random index (`BSRandom::Int`), checks the candidate's own `TESCondition` (same
    vtable-slot-0x268 pattern as `VisitBranchNode`), and calls `BGSStoryManagerQuestNode::
    ShouldRunQuest` as an additional filter. On success, records the fire-timestamp and marks the
    node dirty (vtable slot 0x68, arg `0x80000000` — the same dirty-flag convention used everywhere
    else in this engine, see `TESQuest::SetStage` above).
  - Supports a "keep selecting multiple" mode gated on a node flag and a max-count field
    (`node+0xc0`) — a single story-manager node can fire more than one quest per evaluation if
    configured to.
- **`VisitQuest`** — the terminal step once a specific quest is chosen: evaluates the quest's own
  `TESCondition` (at `quest+0x198`), then calls **`TESQuest::FillAliases`** to populate the quest's
  aliases from the story event context — confirming alias resolution happens AT SELECTION TIME, not
  lazily. Also references a global **`TESQuest::pCurrPartialQuest`** pointer — a single "quest
  currently being partially resolved across multiple tree branches" slot, suggesting a quest's
  aliases CAN be filled incrementally across more than one story-manager branch in the same pass.

**Debug/audit trail:** every branch of all three visitor methods calls
`BGSStoryManager::AddLogEntry(logEntryType, event, node/quest, ..., ...)` with a distinct numeric
`LOG_ENTR_T` code per decision outcome (condition failed, already started, on cooldown, selected,
etc.) — this is the backing data for whatever debug UI/console command surfaces story manager
decisions (not itself investigated, but the hook point is now known: `BGSStoryManager::AddLogEntry`).

This closes out what was previously the single biggest open question in this doc — how Bethesda's
"radiant" quest/event selection actually works is now a decompile-confirmed algorithm, not a guess.

## Confirmed: the cooldown/reset system `VisitQuestNode` calls into

Three more `BGSStoryManagerQuestNode` methods decompiled, filling in the cooldown mechanism referenced
above:

- **`GetQuestHoursUntilReset(node, quest)`** — a hash table on the NODE (`node+0xb8`, keyed by a CRC
  of the quest pointer) holding **per-quest-candidate cooldown overrides**; falls back to a lookup
  with key CRC-of-null (a node-wide default entry) if the specific quest has no override, or `0.0` if
  neither exists. So CK authors can set a custom reset time per candidate quest on a story-manager
  node, not just one blanket value for the whole node.
- **`ShouldRunQuest(node, ownerNodeID, candidateIndex, debugFlag)`** — the actual per-candidate gate:
  rejects if the quest was already claimed by this exact node in the current pass (compares the
  quest's own "last claiming node" field, `quest+0x20`, written by `VisitQuest`/`VisitQuestNode`
  elsewhere); rejects if already running (`BGSStoryTeller::GetIsQuestStarted`); if the node has a
  nonzero reset-hours value, compares `Calendar::GetDaysPassedExact() - lastFiredTimestamp` against
  it and rejects if still on cooldown; checks a quest flag bit (`quest+0xf5` bit 0 — reads like a
  "never auto-reset" CK checkbox) that can force-reject even off cooldown; and checks a node-level
  "respect cooldown" flag (`node+0x3e` bit 0) as a final gate.
- **`ResetRunStateForAllChildren(node, ownerNodeID)`** — called from `VisitQuestNode`'s fallback path
  when a pass exhausts all "fresh" candidates without picking one: iterates every quest candidate on
  the node, and for any whose cooldown has meanwhile expired (same day-count math) and isn't flagged
  "never auto-reset", clears its claimed-node field and last-fired timestamp (recycling it back to
  eligible) and marks the node dirty. This is the mechanism that lets a story-manager node "start over"
  and re-consider previously-picked-but-now-off-cooldown quests in the same evaluation, rather than
  permanently exhausting its candidate pool.

**Also decompiled `BGSStoryTeller::GetIsQuestStarted`** (RVA `0xd9f10`, the actual check
`ShouldRunQuest`/`VisitQuestNode` call): `BGSStoryTeller` maintains **three separate parallel
quest-pointer arrays** (`storyteller+0x58`/`+0x68`, `+0x40`/`+0x50`, `+0x70`/`+0x80`, each a
pointer+count pair) and the quest counts as "started" if it appears in ANY of the three — almost
certainly active/completed/failed (or similarly-partitioned) quest-state lists, though which is
which isn't confirmed from this decompile alone. **`BGSStoryTeller::AddWaitingStageForQuest`**
(RVA `0x7faac0`, called from `TESQuestStage::SetDone`) uses a scatter-table keyed by quest form ID
mapping to an array of `(stage, logEntryIndex)` tuples — the queue structure backing whatever reads
"waiting stages" later (not itself traced).

## Confirmed: `BGSBaseAlias` resolution — how an alias binds to a live reference

Decompiled `GetAliasedRef` / `DoGetAliasedRef` / `GetAliasedRefAt` (RVAs `0x5dcf60`/`0x5f3840`/
`0x5f39f0`):

- **`GetAliasedRef`** is a thin thread-safety wrapper: takes `quest+0xd0` (a `BSReadWriteLock`) as a
  read lock, calls `DoGetAliasedRef`, releases. Standard read-lock-around-a-lookup pattern.
- **`DoGetAliasedRef`** is the real resolution: aliasID `0xFFFFFFFE` is a hardcoded sentinel (returns
  a fixed handle constant — reads like a "player alias" special case, not yet confirmed). Otherwise
  calls `GetAliasIndex(quest, aliasID)` to map the alias's form ID to an array slot, then reads
  `quest->aliases[idx]` — a flat array at `quest+0xb8`, **24 bytes (`0x18`) per alias slot**. Each
  slot is a tagged union: bit `0x80000000` of the first dword decides whether the handle is stored
  **inline** (slot dword 2 IS the handle) or **indirect** (slot dword 2 is a pointer to the handle) —
  presumably fixed ref-aliases vs. dynamically-resolved aliases (find-matching-object, etc.).
- **`GetAliasedRefAt`** is the multi-ref variant (aliases that can hold more than one matched
  reference, e.g. a location/collection alias): same `0x80000000` tag bit, but decides between an
  **inline small array** vs. a **pointer to a heap array** of handles, indexed by a sub-index
  parameter.

This is real, previously-undocumented alias storage layout (CommonLibF4 has no `BGSBaseAlias`
resolution API at all) — useful for any future mod that needs to read a quest's live alias bindings
directly from memory rather than via Papyrus.

**`TESQuest::GetAliasIndex`** (two overloads, RVA `0x5e2ba0` taking an alias form ID and `0x5e2c50`
taking a `BGSBaseAlias*` directly) is the function `DoGetAliasedRef` calls to do the ID→index
mapping: it's a hash table (open-addressing, `quest+0x178`/`quest+0x184` = table/mask, chained via
low 16 bits, index in high 16 bits — the exact same hash-bucket shape as `TESQuest::SetStage`'s stage
lookup) keyed by the alias's own form ID, validated against the STATIC alias-definition array at
`quest+0x70` (`BGSBaseAlias*[]`, each entry's own `+0x18` field holds its alias ID). This is a
*different* array from the RUNTIME resolved-binding array at `quest+0xb8` that `DoGetAliasedRef`
reads — i.e. the quest keeps two parallel arrays: the CK-authored alias definitions, and the live
per-alias resolved handles, joined by a shared index from this hash lookup.
